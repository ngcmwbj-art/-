# 毎日の改善会議（10案 → レギュラー3人＋日替わりゲストで議論 → 5案）

対象は、今のリポジトリ（またはユーザーが指定したもの）で作っているゲーム。ゲーム名・遊ぶ人・環境・これまでの不満は、README・仕様書・会話の流れから読み取る。分からない所だけユーザーに短く聞く。

## 手順

### 1. 材料を集める
- ユーザーから今日の「遊んだ感想」があれば、それを最優先の材料にする。なければ一言だけ聞いてよい（返事がなくても進める。定期実行のときは聞かずに進める）。
- ゲームのコードと仕様書を読み、今の作りと弱点をつかむ。
- 前回までの会議結果があれば読み、同じ案を繰り返さない（記録は `docs/kaizen/` に残す。下の 7 を参照）。

### 2. 改善案を10個出す
- 人気ゲームで実際に効いている仕組みを参考にし、「どのゲームの何か」を必ず書く。
- 感想で出た不満を解決する案を、少なくとも2つ入れる。
- 前回までに見送った案も候補にしてよい（状況が変わった理由を添える）。
- 各案は「何をするか／参考にしたゲーム／このゲームではどうするか」を1〜2行で書く。

### 3. 会議のメンバーを決める（レギュラー3人＋日替わりゲスト1〜2人）
レギュラー（毎日参加）：
- **UI/UX担当**：分かりやすさ、操作のしやすさ、画面のごちゃつき
- **ゲームデザイン担当**：面白さ、もう一度遊びたくなるか、人気が出るか
- **技術担当**：実装の手間（小/中/大）、端末の負荷・発熱、バグの出やすさ、今のコードとの相性

日替わりゲスト（1〜2人。前回と違う人を選び、今日の10案に合う人を優先）：
- **初めて遊ぶ人**：説明なしで何をすればいいか分かるか
- **子ども（小学生）**：楽しいか、難しすぎないか、言葉が分かるか
- **辛口レビュアー**：あえて全案の弱点を突く反対役
- **SNS担当**：短い動画やスクショで人に見せたくなるか
- **アート担当**：見た目の統一感、キャラの魅力
- **サウンド担当**：音で気持ちよさや状況が伝わるか
- **ターゲット層代表**：このゲームを遊んでほしい人（仕様書やユーザーの情報から決める）

会議の最初に、今日のゲストが誰で、なぜ選んだかを1行で書く。

### 4. メンバー全員をサブエージェントとして同時に立ち上げる
- 全員を1回の応答でまとめて起動し、同時に動かす。
- 全員に同じ10案、ゲームの説明、ユーザーの感想、コードの場所を渡す。コードは読んでよいが、編集はさせない。
- 各メンバーには次の4つを600字程度で出させる。
  1. 10案それぞれの短い評価
  2. 今すぐやるべきトップ5（順位付き）
  3. 落とした案の理由
  4. 他のメンバーへの反論・提案を1〜3個
- 全員の結果がそろうまで待つ。結果を予想して先に書かない。

### 5. 議長として結果をまとめる
- 全員の順位を表にする。
- 1位=5点〜5位=1点で合計し、上位5つを選ぶ。ゲストの票もレギュラーと同じ重さにする。
- 同点のときや意見が割れたときは、反論を読んで議長が判断する。2つの案を合わせてもよい。判断の理由は1行で書く。
- メンバーから出た条件（例：「発熱しない範囲で」「オン・オフできるように」）は、採用案に反映する。
- 辛口レビュアーが出た日は、その指摘への答えを各採用案に1行で添える。

### 6. 日本語で報告する
1. 今日のメンバー（ゲストと選んだ理由）
2. 全員の順位表
3. 今日の改善案ベスト5（各案：何をするか、なぜ良いか、手間、誰の意見を取り入れたか）
4. 見送った案と理由（短く）
5. おすすめの実装順

最後に「どれを実装しますか？」と聞く。**ユーザーが選ぶまで実装はしない。**

### 7. 記録を残す
`docs/kaizen/YYYY-MM-DD.md` に、10案・メンバー・順位表・ベスト5・見送った案を短く書いて残す（次回の重複防止用）。リポジトリにコミットするのは、ユーザーが実装を選んだときに一緒にでよい。

## 注意
- 専門用語は使わず、ゲームに詳しくない人にも分かる言葉で書く。
- 議論は「別々に評価した結果を議長がまとめる」形。実際より大げさに書かない。
- メンバーは全員同じAIなので、人数を増やすより、役割の違いをはっきりさせることを大事にする。
- 実装するときは1つずつ作り、テストしてから次へ進む。
